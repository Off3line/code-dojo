# Multiplayer Tic-Tac-Toe Kata (React + socket.io)

Welcome! In this dojo you build the **front-end** for a multiplayer Tic-Tac-Toe game.
The **server is already built and running for you** — it owns all the rules. Your job is a
React client that talks to it.

You'll work **spec-driven**: instead of guessing, you let the server's *spec* (its contract)
tell you exactly what to send and what to expect, then build your UI to match.

---

## The end goal

A working React client where two players can:

1. **Join a lobby** and see the other waiting players.
2. **Challenge** a player; the other side gets an **invitation** to accept or decline.
3. Play a **best-of-three** match — click cells, take turns.
4. See the **scoreboard** (rounds won) and a clear **win / lose / draw** result.
5. Return to the lobby and play again.

You don't write any game logic (who won, whose turn, illegal moves) — the **server decides
all of that**. Your client **sends intentions** ("I want to move here") and **renders
whatever state the server reports**.

This is a **React fundamentals** exercise: component state, effects, rendering from data,
and reacting to a live event stream. It's intentionally incremental — **you are not expected
to finish everything.**

## Setup

### 1. The server (already running — you just use it)

You don't run or see the server. It's **already running** at the **`SERVER_URL`** you were
given, and you interact with it **only over its endpoints** — there are no server files to
install or read.

**First thing to do:** open **`SERVER_URL/protocol`** in your browser
(e.g. `http://ttt-server.example.internal:3001/protocol`). This returns the **entire
contract as JSON** — every message you can send and every message the server sends you. It's
generated by the server, so it's never out of date. **When in doubt, check `/protocol`.**

### 2. Your client (this is what you build)

```bash
cd client
npm install
npm run dev
```

Two things to wire up for the networked setup:

1. **Point the client at the server.** In `client/src/App.jsx`, set the connection address
   to your `SERVER_URL`:

   ```js
   const SERVER_URL = "http://ttt-server.example.internal:3001"; // the value you were given
   ```

2. **Make your client reachable.** If you've been given a `CLIENT_HOST` to open your app
   from another machine, expose the dev server:

   ```bash
   npm run dev -- --host
   ```

   then open your **`CLIENT_HOST`** in the browser.

The starter already connects, has a **Join lobby** button, and prints every event the server
sends into a log panel. That log is your friend — it shows real payloads as they arrive.

## Spec-driven workflow

> **Read the spec → keep the tests green → build the UI → repeat.**

You have **one source of truth** for what the server expects, available three ways:

1. **The live spec endpoint — start here.** `SERVER_URL/protocol` (see above).
2. **The contract tables** below — the same information with examples.
3. **The pre-flight tests** in `client/test/` — an executable description of the behavior
   your client should have (see *Test your client* below).

The build loop:

1. Look at the next failing UI test and the matching entry in `/protocol`.
2. Build that piece of UI.
3. Watch the test go green.
4. Repeat until the suite is green — then connect to the real server and play.

## How the game works

1. A player clicks **Join lobby** → the client emits `joinLobby`. The server adds them to
   the **lobby** (the list of waiting players) and broadcasts the updated list to everyone
   waiting (`lobby` event).
2. Each waiting player sees all the others (but not themselves) and can **click a player to
   invite them** (`invite`). The invited player gets a popup (`inviteReceived`) and can
   **accept or decline** (`respondInvite`).
3. On accept, the server starts a **match** between those two. The **inviter plays X**, the
   accepter plays **O**. Both leave the lobby (and their other pending invites are cancelled).
4. A **match is best-of-three rounds**. Each round is one tic-tac-toe board.
   **First player to win 2 rounds wins the match.**
5. A **drawn round is replayed** (nobody scores, the round number stays the same).
6. The **starting player alternates** each round (round 1 = X starts).
7. When someone reaches 2 wins, the server announces the result and ends the match.
   Both players return to the menu and can **Join lobby** again.
8. If a player disconnects mid-match, the match is **aborted with no winner** and the
   opponent is told to return to the menu.

## The socket contract (your spec)

> **Quick live reference:** the running server serves the whole contract as JSON at
> **`GET SERVER_URL/protocol`** — open it in a browser or `curl` it to see every event and
> payload shape. It's generated by the server, so it's always up to date.

Connect to your **`SERVER_URL`** with `socket.io-client`. Board cells are indices
**0–8**, left-to-right, top-to-bottom:

```
 0 | 1 | 2
-----------
 3 | 4 | 5
-----------
 6 | 7 | 8
```

### Client → Server (what you send)

| Event           | Payload                      | Meaning                                   |
|-----------------|------------------------------|-------------------------------------------|
| `joinLobby`     | `{ name }`                   | Enter the lobby (list of waiting players) |
| `leaveLobby`    | _(none)_                     | Leave the lobby                           |
| `invite`        | `{ toId }`                   | Invite a waiting player (their socket id) |
| `respondInvite` | `{ inviteId, accept }`       | Accept (`true`) or decline (`false`)      |
| `makeMove`      | `{ index }` (0–8)            | Place your mark in a cell                 |

Once a match starts there is **no leave event**: you exit a match only by finishing it or
disconnecting.

### Server → Client (what you listen for)

| Event            | Payload | Meaning |
|------------------|---------|---------|
| `lobby`          | `{ players: [{ id, name }] }` | The current waiting players. Sent whenever the list changes. Filter out **your own** `id` (`socket.id`). |
| `inviteReceived` | `{ inviteId, from: { id, name } }` | Someone invited you — show a popup to accept/decline. |
| `inviteSent`     | `{ inviteId, to: { id, name } }` | Confirmation that your invite was delivered. |
| `inviteDeclined` | `{ inviteId, by: { id, name } }` | A player declined your invitation. |
| `inviteCancelled`| `{ inviteId, reason }` | An invite is no longer valid (`"left"`, `"matched"`, `"unavailable"`). |
| `matchFound`     | `{ gameId, symbol, opponent, bestOf, scores, round, yourTurn }` | A match started. `symbol` is `"X"` or `"O"`. |
| `gameState`      | `{ board, currentTurn, status, round, scores }` | Sent after every move. `board` is a 9-cell array of `null \| "X" \| "O"`. |
| `roundOver`      | `{ winner, line, board, scores, round, nextRound }` | A round ended (`winner` is `"X"`, `"O"`, or `"draw"`). `board` is the final 9-cell board (incl. the winning move). `line` is the 3 winning cells, or `null`. A draw has `nextRound === round`. Unless the match is over, a fresh `gameState` follows for the next round. |
| `matchOver`      | `{ matchWinner, scores }` | The match is decided. The server then ends the game. |
| `errorMsg`       | `{ message }` | Your move was rejected (out of turn, occupied cell, etc.). |
| `opponentLeft`   | _(none)_ | Your opponent disconnected; the match was aborted. Return to the menu. |

`scores` is always `{ X: <round wins>, O: <round wins> }`. `round` is 1-based.

### A minimal client recipe

```js
import { io } from "socket.io-client";

const SERVER_URL = "http://ttt-server.example.internal:3001"; // the value you were given
const socket = io(SERVER_URL);

socket.emit("joinLobby", { name: "Alice" });

socket.on("lobby", ({ players }) => {
  // render everyone except yourself; clicking a player invites them
  const others = players.filter((p) => p.id !== socket.id);
});

// invite a player you clicked:
socket.emit("invite", { toId: somePlayerId });

socket.on("inviteReceived", ({ inviteId, from }) => {
  // show a popup; on the user's choice:
  socket.emit("respondInvite", { inviteId, accept: true /* or false */ });
});

socket.on("gameState", ({ board, currentTurn, round, scores }) => {
  // render the 3x3 board + scoreboard
});

// when a player clicks an empty cell `i`:
socket.emit("makeMove", { index: i });
```

## Test your client before connecting

The starter ships with a **pre-flight test suite** so you can validate your client
**offline — no server needed**. It mocks `socket.io-client`, so the tests run instantly and
let you confirm everything is wired up before you point at the real server.

```bash
cd client
npm install          # first time only
npm test             # run once
npm run test:watch   # re-run on every change (great while building)
```

There are two tiers:

- **`test/readiness.test.jsx`** — a smoke check that your client loads, survives every
  server event without crashing, and joins the lobby. **These pass on the starter already.**
  If one goes red, you removed some necessary plumbing.
- **`test/ui.test.jsx`** — these **fail at first** and turn green as you build the lobby
  list, the invite popup, and the board. They describe the behavior the server expects.

### The test "UI contract"

So the tests can find elements in **your** design, expose this minimal set of hooks. Style
everything however you like — only these identifiers matter:

| What | Hook the tests look for |
|------|-------------------------|
| Join button | a `<button>` whose text is **"Join lobby"** (+ a text input for the name) |
| Invitable player | `data-testid="invite-<playerId>"` on each other player's invite control |
| Invitation popup | `data-testid="invite-accept"` and `data-testid="invite-decline"` |
| Board cells | `data-testid="cell-0"` … `data-testid="cell-8"` |
| Your symbol | `data-testid="my-symbol"` (renders `"X"` or `"O"`) |

`test/mockSocket.js` is the fake socket — read it to see how the tests simulate the server,
but you shouldn't need to edit it.

## Suggested order

1. Show connection status and a **Join lobby** button (the starter already does this).
2. Render the lobby list from `lobby.players` (hide yourself); click a player to `invite` them.
3. Handle `inviteReceived` with an accept/decline popup; emit `respondInvite`.
4. On `matchFound`, switch to the game screen and show your symbol.
5. Render the board from `gameState.board`; click an empty cell on your turn → `makeMove`.
6. Add the scoreboard (current `round` and `scores`).
7. Handle `roundOver`, `matchOver`, and `opponentLeft` with clear UI transitions.
8. Polish: highlight the winning `line`, disable the board between rounds, etc.

If your UI faithfully reflects the server's state and a full best-of-three plays cleanly,
you are succeeding. A lobby that can start a game and a board you can play is already great.

## Rules of thumb

- **The server is the judge.** Treat it as a black box: you only have its endpoints, the
  `/protocol` reference, and this guide — there are no server files to read or change. If
  your UI lets you do something illegal, the server rejects it with `errorMsg`, so trust the
  server, not local guesses.
- **Render from server state.** Don't track the board yourself; draw whatever the latest
  `gameState` says.
- **Check `SERVER_URL/protocol`** whenever you're unsure what to send or what a payload contains.
- **Keep the readiness tests green** as a safety net while you build.

## Use of AI Tools

The use of AI tools (ChatGPT, Copilot, etc.) is explicitly encouraged, with clear intent.

✅ Appropriate uses

- Explaining React, JSX, hooks, or socket.io concepts
- Explaining error messages or unexpected behavior

- Asking why something renders the way it does

🚫 Not appropriate

- Asking AI to implement the whole client for you
- Copy-pasting a full finished app
- Letting AI decide your component design end to end

Rule of thumb: use AI like a senior colleague who explains things, not like someone who
writes the code for you.
